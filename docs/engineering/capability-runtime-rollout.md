# Capability runtime deployment

This document records deployment and rollback information for the
`capability-oriented-chat-runtime` change. The engineering behavior contract is
in `docs/engineering/skills/uk-chat-runtime.md`.

## Database deployment

The capability runtime does not use a separate database. Runtime persistence
obtains the existing SQLModel engine from `DATABASE_URL`, which is also used by
saved conversations. Alembic commands use the explicit
`ALEMBIC_DATABASE_URL`.

- Production configures both URLs for the existing PostgreSQL database. The
  deployment workflow invokes the Modal `migrate` function, which runs
  `alembic upgrade head`, before deploying the API.
- Local Docker Compose derives both URLs from its development PostgreSQL
  settings, waits for PostgreSQL health, runs a one-shot `migrate` service, and
  starts the backend only after migration succeeds.
- Tests construct temporary SQLite repository schemas by default. Set
  `CAPABILITY_TEST_POSTGRES_URL` only to a disposable PostgreSQL database for
  repository and migration-lifecycle checks.

Alembic revision `0001` is the CLI-autogenerated parentless baseline for the
pre-branch `chat_conversations` schema. Revision `0002` is the CLI-autogenerated
additive revision that creates:

- `capability_artifacts`;
- `waiting_capability_invocations`;
- `capability_invocation_traces`;
- `capability_turn_receipts`; and
- `capability_call_receipts`.

Revision `d97a20592837` adds the invocation trace debug input and output
columns. Revision `9526d8c80914` is the CLI-autogenerated additive revision that
creates `conversation_contexts` for the latest versioned typed entities, facts,
pending requirements, and focus for each conversation.

Alembic ignores Supabase-owned billing and authentication objects and neither
reads nor changes superseded `analysis_*` tables. Backend startup validates the
current Alembic revision and performs no schema mutation.

Complete population simulation objects remain request-local; only validated
aggregate values and provenance are durable.

## Application deployment and rollback

The application contains one implementation of `POST /chat/message`. It always
runs the capability-oriented chat service and emits `invocation_activity` for
operation status. There is no environment-variable selector and no inactive
copy of the preceding chat loop in the current build.

To roll back:

1. Deploy the preceding known-good application image or commit.
2. Leave the additive capability tables in place; application rollback does
   not require a database downgrade.
3. Confirm the deployed health endpoint and one representative public chat
   turn before restoring traffic.

Do not manually delete capability records during an application rollback.
Normal conversation deletion removes the records owned by that conversation.

## Resource requirement

Population acceptance must run in an environment with enough memory to load the
managed dataset. Local measurements showed that an 8.32 GB Docker allocation
was insufficient. The Modal web function is configured with 16 GB. Local
population testing requires a correspondingly larger Docker allocation.

Before deployment, verify:

- public completion, clarification, unsupported, failed, cancelled, replay,
  and identifier-conflict outcomes;
- model-usage and one-time billing accounting;
- complete public and private invocation records;
- population calculation completion and latency in the target environment;
- the frontend activity presentation in normal and debug modes.

Run the manual deployed population evaluations documented in
`docs/engineering/skills/ai-evals.md` when the managed dataset and explicit
evaluation credentials are available.

## Verification record for this change

The completed local checks on 2026-08-27 were:

- strict mypy validation of all 31 configured typed runtime modules;
- 372 passing backend tests, 14 environment-dependent skips, and 83.18%
  aggregate backend coverage against the required 80%;
- 74 passing frontend tests, frontend coverage reporting, and a successful
  optimized Next.js build;
- 70 passing offline AI evaluations, no failures, and 24 live or
  environment-dependent skips; and
- an Alembic upgrade, schema comparison, downgrade, and re-upgrade against the
  local Docker PostgreSQL database, ending at revision `9526d8c80914`.

The offline evaluation intentionally exercises an invalid made-up parameter and
therefore logs the rejected PolicyEngine reform traceback while still passing
that case. A full managed-dataset population calculation remains dependent on a
runtime with sufficient memory and managed-dataset access. The debug activity
presentation also requires manual visual confirmation under the repository's
visual-verification policy.
